# DevJay architecture and development

DevJay is a macOS-only Go application with Wails v3 beta.23 and embedded HTML/CSS/JavaScript. Application sources live in `cmd/devjay/`. All Go files belong to package `main`; there is no frontend package manager or bundler. The application manages its own windows and observes local folders, Git repositories, and optional GitHub.com PR state. It does not own editors, agent sessions, or macOS Spaces.

## State and event flow

`cmd/devjay/main.go` embeds its adjacent `frontend/` and creates the strip, Settings, Site windows, and action confirmation UI. The shared frontend selects its view through URL parameters (`site`, `settings`, `viewer`, or `actions`). The strip is a nonactivating AppKit window, so clicking it does not necessarily give DevJay keyboard focus.

`siteManager.run` processes closures sent through `m.send`. Background Git readers and event handlers return results through this queue. The manager's mutex protects runtime membership against shutdown; it is not a substitute for the queue. Native bridges marshal AppKit work onto the main thread.

The manager combines configuration, Git state, and a batched native window snapshot into `appSnapshot`, emitted as `devjay:snapshot`. A deadline-driven manager wakes for commands, coalesced native/filesystem events, recovery deadlines, and actual monitoring work. Native Space notifications refresh the active-card state immediately, with two bounded settling checks; a 30-second safety sweep catches missed events. Window positions are cached independently of Git and agent publications. Snapshots are delivered directly to visible windows, with Site/viewer snapshots limited to their own Site and unchanged content suppressed. Initial documents and explicit requests still get a response. Hidden documents defer subsequent rendering and pause working-dot animation; native visibility combines visible, active Space, minimized, and occlusion state, independently of application activation. Revealing a window delivers fresh state. Layout persistence uses notifications plus one shared tolerant 60-second fallback while awake instead of per-window timers. Frontend events use the `devjay:` namespace. Action preparation and confirmation require an application acknowledgment, with bridge failures shown in the UI.

Each Site starts `watchGitWithControl` once its window is ready. Recursive FSEvents observations cover the actual worktree and Git/common directories, including linked-worktree indirection. Streams are registered before status reads; coalesced events debounce for 300 ms with a 1.5-second maximum, and dropped/root-change events invalidate the observation. A two-minute safety reading reconciles missed events; unavailable observation/readings retry after 15 seconds. Background Git runs with optional index writes disabled. Becoming active requests a fresh local read. Display/session sleep cancels background reads and pauses observation; resume rebuilds it. Full remote/GitHub reads run independently, one minute apart for active Sites and five minutes apart for quiet Sites, measured after completion. Normal cache age does not produce an error or stale warning; the last successful check remains available in the card tooltip. Failed and not-yet-completed checks remain explicit. Cache identity and refresh generations reject obsolete results after checkout changes. Transient failures preserve the last complete reading with an explicit cached/unavailable label. A cached remote-rewrite event is cleared when a complete comparison shows no local-only commits or no incoming commits. Thus a remote commit amended before the checkout incorporates it remains an ordinary fast-forward update. Unknown comparisons and diverged histories retain the event warning; independently verified upstream-replacement evidence still marks affected history as rewritten.

Full GitHub refreshes enrich displayed PRs with one bounded GraphQL author query (up to twenty PRs), using `viewerDidAuthor` from the same authenticated request to identify other authors. Missing authors, unknown ownership and failed queries produce no badge. Only HTTPS GitHub avatar URLs are passed to the WebView; images load with no referrer and fixed dimensions, with initials as the load/error fallback. The footer keeps app icons on the left and author avatars on the right in both card views. Author metadata follows the existing branch cache identity and survives lightweight CI updates for the same repository/PR; no extra polling is added.

The existing open-PR `gh pr list` query includes `statusCheckRollup` alongside the pushed head identity. Each `PullRequestLink.ciState` conservatively aggregates CheckRun and legacy StatusContext results independently of review/draft state. Confirmed failures and action-required checks remain visible when other checks are pending; missing, stale, malformed, or potentially truncated results cannot become a successful rollup. Cancelled and skipped/neutral outcomes remain distinct. GitHub CLI exports at most 100 contexts without pagination metadata, so a 100-entry result is treated as potentially incomplete unless it already establishes failure, action required, or pending work. While CI is pending, a separate bounded PR-list query runs every thirty seconds without fetching Git or downloading review comments. Failed lightweight checks show unknown and retry after one minute. Full refreshes take precedence when both are due. Partial results retain remote/review caches, honor branch generations and cache identity, and cannot overwrite a newer local read failure. Approved and merged PR tags use green; CI failure or action-required tags override that color with red plus a failure/action symbol, with CI and review text in their accessible name and the existing nonactivating native tooltip. PR-only changes refresh that tooltip even when development-app status is disabled.

Development app labels use a separate read-only observer. Supported apps include IDEs, terminals, and the standalone Codex/ChatGPT and Claude main app bundles; helper processes and URL handlers are excluded. The batched AppKit snapshot supplies Site window numbers and desktop positions. One background worker scans WindowServer metadata and supported running application identities for all Sites, matching single-Space membership through runtime-loaded SkyLight functions. It does not read window titles or window pixels, send Apple Events, inspect terminal contents, activate windows, or alter the file-opening editor preference. All supported matches are retained; this is desktop co-location, not verified project ownership. Results flow through the manager queue. Changed Site/window/display identities invalidate old readings and reject stale in-flight results. Window/process discovery has a 30-second fallback and is invalidated by native application/Space events or changed placement. Separate activity reads revalidate only known process IDs, start times, cwd and ancestry: two seconds after completion while working/waiting or during a short activity burst, otherwise twelve seconds. Claude registry filesystem events request an earlier reading; newly seen registry PIDs request discovery. All work shares one in-flight worker and a 250 ms minimum spacing, and pauses with UI recovery during display/session sleep. Wake invalidates the cache. Missing APIs or unknown desktop membership produce an unknown state rather than a false empty result. No subprocesses, per-Site polling loops, or persisted app assignments are added.

`SiteConfig.showIDEStatus` defaults to true when absent and is exposed in snapshot preferences. Only Settings can change it. Disabling clears readings, rejects pending results through the monitor generation, and prevents new scans; an already running native metadata call may finish. Re-enabling requests a fresh scan while preserving the one-worker limit. Saving a preference failure leaves the previous setting in effect and republishes authoritative state. The display has one icon presentation, controlled only by the on/off setting. Legacy `appStatusView` values are ignored when loading and omitted on the next ordinary save. The indicator groups a 22-point host icon with 16-point agent icons in one activation button, or shows the host icon alone when no agents are detected. App groups wrap intact and have accessible names and initials fallbacks. Within the app indicator, only the capsule/single icon carries `data-app-tooltip`; their row, padding, and gaps are not hover targets. Hover text is a short app/agent label such as “GoLand with Claude Code and Codex.” App status hover uses the always-active AppKit tracker and a dedicated mouse-ignoring, nonactivating strip because WebKit title tooltips do not reliably appear on the inactive strip. After a 400 ms delay, the tracker rereads bounded `data-app-tooltip` text and normalized DOM bounds, rejecting stale replies before showing the content-sized strip within the anchor monitor, capped at 380 points wide. It never requests activation, key/main status, or a Space move. Exit, clicks/scrolling, window/Space changes, application switching, and sleep cancel pending/visible tooltips. Only strip/Site senders may request a tooltip refresh when their relevant snapshot content changes; ordinary Git/icon updates do not add hover work. The native refresh is a no-op unless a tooltip is already pending or visible.

Installed app icons come from `NSWorkspace.iconForFile` and are rasterized to transparent 40×40 PNGs on the AppKit thread. A bounded cache keyed by bundle path and modification time holds the small encoded images, including failed lookups. Only initial misses visit AppKit; subsequent scans reuse the cached data. No app is activated, and no screen pixels or downloaded icon assets are used. The frontend accepts observed host icons as PNG data URLs only. Two bundled PNG identity marks in `frontend/icons/` represent Claude Code and Codex independently of whether their desktop apps are installed; only the fixed agent-name allowlist selects those asset paths. Loading these static assets adds no polling or app discovery.

The same worker adds best-effort embedded Claude Code/Codex presence from a bounded native process snapshot. It recognizes native executable paths, reads candidate working directories, and walks parent IDs, including root-owned login intermediates. Go resolves symlinks off the UI thread, chooses the longest matching Site folder, then requires the owning editor/terminal PID among windows on that Site desktop. Native iTerm persistent shell servers have a narrowly recognized helper location and use iTerm's bundle identity instead of its independent GUI PID; a same-desktop iTerm window is still required. Nested/ambiguous folders, unrelated or detached processes, and desktop AI helper processes are not assigned to another Site by fallback. Folder paths participate in monitor generation checks, including Sites whose native window is not yet available. Only deduplicated agent names, `waitingAgents`, `workingAgents`, and display metadata (app name, icon, window count) reach the frontend; intermediate process IDs, start times, ancestry and cwd are retained only in the in-memory discovery cache and are never persisted or sent to the frontend. Presence is inferred, not exact window/tab association. No argument/environment buffers, shell commands, terminal APIs, session databases or OCR are used; the manager schedules bounded discovery and activity reads independently.

The worker also reads explicit working/waiting metadata, rebuilding the result each scan so resumed, exited, unreadable, and unsupported sessions cannot retain old activity flags. Claude Code's `~/.claude/sessions/<pid>.json` registry is read only for live native Claude candidates. An owned directory descriptor anchors no-follow, nonblocking file opens; files must be owned regular files no larger than 16 KiB. The typed decoder retains only identity, cwd, status, and timestamps. An activity record must match the live PID, Darwin PID domain, kernel process start, ordered timestamps, and canonical cwd. Timestamps advance on transitions rather than heartbeats, so a valid long-lived dialog is not expired merely for its age. This registry is an observed Claude 2.1.283/2.1.284 implementation detail; missing or changed schemas remain unknown. Only `busy` establishes processing. `shell` means the agent is idle with a background shell task still present and does not establish processing; `idle` has no activity marker.

For Codex, one read-only WebSocket connection per scan uses the existing default `~/.codex/app-server-control/app-server-control.sock` pointer. A bounded chain of owned symlinks must resolve to a private, owned Unix socket. The transport cannot connect over the network or follow HTTP redirects and never starts a daemon. The only RPCs are `initialize`, `thread/loaded/list`, and `thread/read` with `includeTurns:false`, plus the `initialized` notification. It never subscribes to or resumes threads, responds to approvals/questions, or reads authentication/configuration files. Limits are two seconds for the caller's entire connection, 64 threads, four list pages, 128 messages, 256 KiB per message, and 2 MiB per scan. Typed results retain only cwd, source, and status; incidental previews and server notifications are ignored. Only `cli`/`vscode` sources qualify. Active threads with `waitingOnApproval` or `waitingOnUserInput` establish waiting; active threads with an explicitly present, empty `activeFlags` array establish working. Missing, null, or unfamiliar flags cannot establish working. Idle, not-loaded, and system-error states do not establish processing. Exact canonical cwd must map all matching live Codex candidates to one Site/host group; competing hosts or unowned candidates make the association unknown. The `vscode` source additionally requires an editor host, while CLI sessions can belong to an editor or terminal. Multiple sessions within that one group aggregate; any verified waiting session suppresses working for that same agent regardless of observation order. The [Codex app-server interface](https://learn.chatgpt.com/docs/app-server) describes thread status; its WebSocket transport is experimental, and the local control socket is version-dependent. This covers only sessions loaded in that daemon; separate stdio servers, desktop apps, custom agent-home locations, and remote sessions remain outside the initial coverage. No hooks or configuration changes are required.

Rendering keeps all observed apps in the snapshot but hides unpaired icons whenever any paired editor/terminal group exists on that card. Confirmed waiting adds a steady amber capsule and a `?` badge on each affected agent, with a short “needs input” suffix in the capsule's accessible name and native tooltip. Working- and waiting-only changes participate in snapshot and tooltip refresh signatures. Absence of the marker is not a verified idle state. A frontend transition cache records when each Site/host/agent first becomes waiting. A finite four-second CSS pulse gives the capsule two diffuse amber glows and radiates a soft background outward from the center of the card, with a quieter second peak. Only the decorative light expands; content and card geometry stay fixed, icons remain opaque, and the active Site border remains visible. The card glow is inset, behind the content, and pointer-transparent. The centered radial background adapts to card dimensions entirely in CSS, without layout measurements or resize observation. The animation uses the elapsed time as a negative animation delay when the DOM is rebuilt, so unrelated snapshots cannot prolong or repeat it. Clearing/removing an observation or disabling app status prunes its transition; `prefers-reduced-motion` keeps only the steady indicator. Confirmed working adds a steady teal capsule, a small `▶` badge on each working agent, and three decorative dots instead of a text label. The dots softly rise and fade in a staggered 1.8-second CSS loop using only opacity and transform. Icons, badges, and layout stay fixed. Negative delays derived from the existing render clock preserve the staggered phase across DOM rebuilds without a JavaScript animation timer. Removing working removes the dots; Reduce Motion keeps them static. The dots are pointer-transparent and remain inside the capsule hover target. Waiting takes priority for the same agent; a mixed-agent capsule remains amber, omits the group-level working dots, and describes both agents in its tooltip. Working transitions do not restart an existing waiting pulse. The status display adds no activation path or separate polling timer; the existing default-enabled setting controls both working and waiting observation.

Changes windows have their own snapshots, selection, cancellation, and generation checks. Opening a category reuses a viewer for that Site (preferring a matching category, then the most recently used); an explicit new-window request bypasses reuse. Requests are routed using Wails' sending window, not just client-supplied Site IDs. Each comparison pins revisions. The History viewer logs the union of the local and comparison tips, counts shared ancestors once, and labels commits by the symmetric difference of those same pinned IDs. Incoming rows remain selectable and use both subdued styling and text. For divergent feature histories, display-only branch-work metadata subtracts local-only commits reachable from the pinned remote default tip. The monitor caches it with the existing rebase comparison by immutable local/upstream/default IDs and verifies raw porcelain counts before accepting it. The viewer independently derives counts and inherited-row labels from its own pinned revisions. Raw ahead/behind counts and every remote-only ID are retained for action guards and history inspection; display metadata cannot enable publication or establish patch equivalence. Commit and file lists use a stable, focusable listbox with an active descendant, so Up/Down and Home/End selection survives row replacement and asynchronous diff reads. List keys and clicks use the existing versioned, read-only viewer requests; loading snapshots guard new requests without making the focused list inert. Same-context loading retains the displayed frame, and unchanged commit/file rows are reused while selection attributes update in place. The usual active-row highlight is the only list focus treatment. Editor discovery retains the previous label while disabling file opening until the new selection is verified. Diff scrolling and modified keys retain their normal behavior. The Changes/History sidebar shares one list area; commit metadata spans the detail area above the history file list and diff. The Changes list groups backend file entries by path while preserving each original file index. Its staged/working-tree controls request the corresponding read-only diff, never stage or unstage files. Local edits remain a separate category; branches without a comparison still show their own history. Legacy local/remote view requests remain supported internally. Visible viewer refreshes run every ten seconds after completion and when Site Git data changes, with at most two background readers. Hidden/off-Space/occluded viewers defer refreshes and request a fresh read when revealed. Refreshes preserve selections by file path/group and commit ID, reject stale generations, and avoid emitting unchanged content. Commit recovery checks bounded ranges around the previous page and the position predicted by the commit-count change; an explanatory note appears if recovery fails. User requests, closure, and display/session pause cancel background reads.

Merged-branch cards also offer returning to the default branch and deleting the local branch. The menu captures the branch, HEAD, upstream, PR number and default-branch identity, revalidates them after menu selection, and enters the existing prepare/confirm flow with deletion preselected. Preparation pins the requested destination; the confirmation still allows keeping the branch. App-icon menus keep their app action, and PR menus keep browser navigation first.

Card context menus use a small synchronous AppKit popup on the main thread, called off the manager queue. The selected action returns to the queue and revalidates Site/window/PR identity. PR links are derived from trusted repository identity; browser commands never accept a frontend URL. A fixed embedded JXA script inspects supported running browsers only on explicit PR actions, with Automation permission and a separate bounded command slot. Default-browser fallback occurs only when the script confirms that no navigation was attempted.

PR navigation errors use a native `NSAlert` window placed with the originating card anchor and existing context-window geometry. Frontend clicks and native menu actions carry the anchor; the backend validates it and resolves the parent from the sender. The alert remains until OK/Escape, without a modal loop or frontend footer update. Browser helper failures retain bounded diagnostic details. Browser windows with null or empty tab lists are skipped before tab lookup or destination selection; default-browser fallback still requires a confirmed no-navigation result. Informational navigation results still use the sender-scoped event.

Incoming/outgoing metrics send a validated `gitAction` hint (`update` or `push`); the backend alone decides eligibility from the current Git reading. Ordinary card/branch menus choose one next step: merged cleanup, verified rewritten-upstream replacement, rebased publication, upstream update, default-branch rebase-and-push, or ordinary push. Replacement requires the same `CanReplaceRemote` evidence used by the Changes window; selection rechecks eligibility and enters the existing replacement preparation/confirmation path. Explicit base/publication rows preserve their dedicated action; app and PR controls retain their existing menus. Update requires a tracked incoming tip, clean local state and no known divergence/rewrite. Push permits edits but rejects incoming or rewritten history. Menu options capture branch, HEAD, upstream and destination identity, then revalidate these and busy state on selection before entering the existing preparation flow. Counts may change after a remote refresh; preparation fetches and checks the actual commits. Each native item has an operation-specific tooltip, with disabled reasons taking priority. No new Git mutation or confirmation path is introduced.

The newer-default-branch status line additionally offers a combined rebase-and-push menu action. Its option captures the local branch/HEAD and default-branch tracking identity; selection rejects changed identities or a newly blocked checkout. Known blocking conditions disable the item with a reason. Authorized card and viewer actions share the manager's preparation path, which fetches and tries the latest default branch in a disposable repository. Native menu selection never confirms a mutation; only the existing confirmation window can consume the prepared plan.

Strip requests supply the originating card's WebView rectangle, validated for finite bounds and clipped natively to the sending WebView. AppKit converts it to screen coordinates and places confirmation and Changes/History windows above the card, horizontally centered on it. If there is not enough room above but the window fits below, it opens below instead; screen-edge clamping keeps it reachable. Other viewers do not displace this card-relative position. Both new and reused viewers use the current request's parent and anchor, including requests arriving before the viewer is ready. Explicit opens can reposition a viewer; background refresh never does. Settings keeps its existing placement. Rebase/publish dialogs use a compact 460×330 layout, show a verified Git-safety result only for a ready plan, and collapse failure details and recovery references.

Independent Site windows expose a rebased-push button below status. Its preparation request is authorized only for that exact ready Site window, the currently observed branch/HEAD, and an enabled rebased-publication option; unrelated senders and other action kinds remain rejected. Pending requests and preparing/running actions disable the button, including across snapshot rebuilds. Bridge failures restore the available action. Its native context menu presents the same guarded publication as the first item. Confirmation still comes exclusively from the confirmation window. Only strip parents use card-relative placement. Viewers opened or reopened from independent Site windows and confirmations from Site or Changes/History windows overlay their parent, centered and clamped to the visible display. The branch chooser receives the Switch button's WebView bounds, clips them natively, and opens ten points to its right while remaining vertically centered over the Changes/History window. Explicit icon clicks and the matching native menu action share `activateDevelopmentApp`. Card sender/Site membership, the current observer target, known app identity, and a single observed PID are checked on the manager queue; AppKit rechecks the running PID’s bundle identifier before navigating to the Site with the existing explicit focus path. A bounded handoff checks every 60 ms for at most two seconds, returning through the manager queue and keeping all AppKit reads on its main thread. Only the same visible, non-minimized, key Site window on the active Space can hand focus to the app. A later explicit window request, superseding icon request, changed Site/app identity, paused UI, or lost app/window focus cancels that handoff. No app launch, project opening, Accessibility access, or background activation is added. macOS still chooses the app’s existing window; DevJay does not select a project or terminal tab. The native menu accepts an optional second action while retaining fixed action tags. ## Git safety boundaries

Monitoring can fetch remote-tracking refs but must not change local branches, HEAD, the index, or working files. Fetches disable hooks, tags, submodule recursion, maintenance, and extra ref mappings. Monitoring and action preparation fetch into random app-owned temporary refs, reject symbolic tracking destinations, and publish tracking updates with an expected old object ID and no symbolic dereferencing. Post-push tracking updates use the same publication guard. Remote cache/worker identity includes the effective remote URL and tracking ref, so URL changes invalidate cached status and outstanding results. Local reads, background network work, and explicit actions have separate command capacity (four, two, and two slots). Fetches are serialized by common Git directory for linked worktrees. Subprocess timeouts start after queueing.

Mutations require preparation followed by an explicit, expiring, single-use confirmation. Implemented actions are branch switching, fast-forward update, return to the default branch after an exact merged-PR match (with optional local branch deletion), conflict-checked rebase and push, ordinary push, verified rebased publication, and verified replacement from a rewritten upstream.

Action dialogs are created on demand, one per Site, with unique Wails sender names. Each owns its parent/anchor, preparation cancellation, generation and action state on the manager queue. Busy checks for action entry points are scoped to the Site; Profile changes and shutdown still account for all running actions. Snapshots deliver an action only to its owning dialog and the same Site's card/viewers. Confirmations validate the registered sending dialog and its single-use plan token; asynchronous results check dialog membership, generation and Site runtime identity. Closing cancels only that dialog's preparation, removes its recovery/visibility registrations and destroys its window. UI close requests carry the rendered generation so a delayed dismissal cannot close a newer operation. Independent repositories share the existing bounded command capacity and can run concurrently; the common-Git-directory mutation lock still rejects overlapping actions in linked worktrees.

A successful result starts a five-second countdown in its dialog, keyed to the completed plan ID. Ordinary snapshots do not restart it. The checkbox beside Done controls the timer: unchecking it or pressing Escape stops it, unchecks the control and shows “Auto closing stopped.” Checking it again starts a fresh five-second countdown. Escape leaves Done available; pending confirmations retain Escape cancellation, and running/failed actions never auto-close. Manual dismissal and document teardown clear timers. WebView reloads rebuild the timer from the completed result.

The branch chooser opens only from a registered Changes window for that Site or its already-bound switch dialog. The chooser is parented to the requesting Changes window and uses a 620×740 dialog (minimum 560×700) with at least six fixed-height branch rows. Catalog reads are on demand, off the manager queue, and list local branches plus locally known remote branches; no polling is added. After publishing the local list, an on-demand worker adds open PR numbers, review state and CI rollups using one bounded GitHub query per repository (up to four repositories and 100 open PRs each). Matching uses configured upstream names or a unique known remote branch of the same name, plus exact head-repository identity; forks are excluded. Missing, failed and potentially truncated results remain explicit. PR enrichment copies the published choices and is discarded if selection, dialog generation or Site identity changed. Sender validation, generation checks, and runtime identity reject unrelated or late requests. Choosing a branch prepares a plan rather than applying it. Preparation checks the selected destination's remote when available, but an existing local branch can still be selected when that check is unavailable. The selected remote is fetched into a temporary private ref so symbolic remote-tracking refs cannot redirect preparation writes into local branches; cleanup uses the expected object ID without dereferencing replacements. Using a newer remote version requires a newly prepared plan and a separate confirmation, with zero local-only commits and strict fast-forward ancestry. Destination ref/configuration, checkout identity, worktree occupancy and exact commits are checked again before application. Fast-forwarding a destination uses an expected-old-commit update without symbolic dereferencing after loading the files safely. The source branch is retained, and remote-only choices create a tracking branch without replacing an existing local name.

Preparation pins the checkout and source/target commits. Applying rechecks identity, branch/upstream, operation state, and other-worktree use where required. Checkout mutations require clean files/index; a push allows staged, unstaged and untracked edits because it publishes the confirmed SHA without touching the checkout. Conflicts and unfinished operations still block a push. Unsupported sparse checkouts, submodules, and hidden index flags are refused. Incoming ignored-file collisions must remain protected. App-owned mutations serialize by common Git directory, but cannot lock out arbitrary external edits or unsaved editor buffers.

Rebases are tried in disposable repositories; only a conflict-free result is installed. Replacement requires the exact local HEAD among the last 256 upstream reflog tips, not patch similarity or commit dates. Ordinary pushes verify the remote result and never force or retry automatically. Rebased publication is a separate `publish` action requiring a clean checkout, same-name origin upstream, and separately confirmed explicit-SHA force-with-lease. Its isolated replay of the current remote branch must match the local rebased prefix tree-by-tree, author-by-author and message-by-message; merge histories, ambiguous bases and series over 256 commits require manual handling. Both preparation and confirmation run the replay with saved/custom/union conflict resolution disabled. The checked latest default tip must already be an ancestor of the local head. The default configuration/tip and publication destination are revalidated before dispatch, and the final server-side lease prevents overwriting a changed branch even after concurrent background fetches. A no-dereference, create-only recovery ref preserves the old remote tip; these backups are retained without completed markers or automatic pruning. The exact remote result is verified even after a command error; no automatic retry follows. This proves Git conflict/history checks against the pinned commits, not semantic correctness or exclusion of later default-branch changes. Local mutations run without deadline cancellation once started; quitting waits for confirmed actions without blocking AppKit.

The combined `rebase-push` action verifies an existing same-name origin upstream and requires its tip to be an ancestor of the original local branch. Before offering confirmation it replays the local branch in isolation with the real committer identity and checks that a separate replay of the remote branch matches the resulting prefix. A remote tip already included in the base is preserved by ancestry. The prepared tree/author/message series is retained privately and must match the repeated trial on application. Nonlinear, ambiguous, signed, empty, or oversized histories stop for manual handling. After rechecking both remote tips, the action preserves original local and remote commits, imports objects without fetching through a named ref, and installs only the checked result with non-forced switches and a no-dereference branch compare-and-swap. A fresh push plan remains bound to the checked result and original remote SHA. Publication rechecks both remote tips and uses the explicit lease; failure leaves the clean local rebase and recovery refs, with no retry or rollback. Local success backups participate in normal retention; remote backups have an `-remote` suffix and remain unpruned. Git checks cannot pre-approve server hooks or guarantee future availability.

Before changing local branches, actions preserve commits under `refs/devjay/backups/<action-id>`. Completion markers under `refs/devjay/completed/` allow pruning to the ten latest verified successes; failed, partial, and legacy backups remain. These refs do not protect uncommitted files. Inspect post-operation state even on errors; never blindly roll back. See the [user guide](USER_GUIDE.md#git-monitoring) for recovery commands and action restrictions.

## Folder recovery and Profiles

Deferred desktop restoration observes the same guard. A separate native reachability pass runs on display changes, wake and window exposure, with two bounded settling passes after display changes. It fits visible app windows to the nearest screen without activating them or saving temporary fallback positions, even while Profile writes are paused. Hidden, transparent, minimized and fullscreen windows are left alone; floating cards preserve Dock overlap while ordinary windows use the usable screen bounds. Each switch cancels outgoing observer callbacks before attaching replacements. Profile creation and native preferences use separate storage, so unavailable native restoration never authorizes overwriting another Profile's layout.

`frontend/settings-navigation.js` mounts five accessible sidebar pages without rebuilding their controls on navigation. `profile-settings.js` owns Profile selection, detected displays, editing scope, and modal creation/rename/deletion. ## Opt-in Claude permission bridge

The CLI mode `--claude-permission-hook` runs before Wails/app startup. It receives bounded `PermissionRequest` JSON on stdin, retains only session/cwd/tool/input, and connects to the current build channel's Unix socket in a private owned `/tmp/devjay-<uid>-<namespace>` directory. The app never sends terminal keystrokes or attaches to Claude's private messaging socket. Missing/unavailable bridges, unsupported tools, invalid input and timeouts produce no hook decision, leaving Claude's ordinary permission flow in charge.

The server bounds concurrent connections (16), initial reads (2 seconds), payload size (64 KiB, with tool input capped at 32 KiB), and pending lifetime (24 hours). Peer credentials must match the user. Native metadata verifies that the peer is this app's hook executable and identifies its nearest live Claude ancestor; the owned no-follow Claude registry must match process start, session-root cwd, timestamps and session ID. Hook cwd may be the session root or an existing subdirectory after resolving symlinks; sibling/outside directories and escaping symlinks are rejected. Card ownership stays with the authenticated session root, and a changed working directory is shown in the approval preview. The server revalidates ancestry/session before replying and every two seconds while a request is pending. Native verification also supplies the original hook helper start time. A validated idle/shell transition after that start retires an abandoned invocation without a verdict, after a two-second startup grace; old idle metadata and busy/waiting remain valid. Reconnects preserve the original helper identity, so an obsolete request cannot become new again. Each invocation has a random one-use token and its own connection. EOF, interruption, shutdown, duplicate decisions and replaced identities cannot send a verdict to another request. A presentation model is derived once from the accepted tool input, off the main thread. It displays literal commands/descriptions, file paths and before/after or write content, with execution/replacement flags and unrecognized fields retained. Control and bidi characters remain visible as escapes. Native attributed text renders this model, with a fixed-frame toggle to the complete original JSON; neither representation changes the decision token or tool input. The only decision payload is allow/deny for that invocation: no updated input, saved permissions, rule changes, tool retries or automatic approval.

The versioned socket protocol acknowledges accepted requests. If that connection drops, the original helper retains only its original invocation in memory and retries the private socket for at most 30 seconds. Reconnection rechecks socket ownership/mode, live peer/Claude identity and session, then creates a new one-use token. The original helper enforces the cumulative 24-hour deadline across reconnects. Explicit handoff, disabling, server expiry, malformed replies and identity rejection terminate without retry or verdict; an unavailable app at initial invocation falls through immediately. App shutdown closes the connection without an explicit handoff. Legacy helpers retain the single-response protocol and cannot reconnect. A lost answer is never replayed or inferred. For development updates, replace the executable atomically at its existing path so an active helper is not truncated or moved; its process path remains valid for reconnection.

The manager queue maps pending processes through the existing most-specific Site and host-window association. A completed discovery releases requests that cannot be shown on a card, allowing a five-second grace for newly connected requests while Site windows and their host inventory initialize; later normal discovery checks release requests still unmapped. The pending connection independently supplies the amber waiting indicator while a hook runs before Claude's own prompt. Prompt details stay in a native in-memory registry; frontend snapshots contain only pending counts. Native callbacks enqueue tokens, and the manager rechecks current Site/host eligibility before consuming them. Disabled development-app status releases pending requests. Confirmed integration settings also gate the server: disabling immediately removes pending tokens and rejects cached hooks and in-flight arrivals until re-enabled. A current Claude waiting reading without a hook request supplies a navigation-only explanatory panel, even when the hook server is unavailable. This status entry is never counted as an answerable request; native controls and manager callbacks both reject allow/deny for it. Resumed or replaced readings invalidate its navigation/setup actions.

The native tooltip tracker passes Site/host identity and screen-space anchor to a separate nonactivating panel after its existing hover delay. The panel clamps to the visible display, stays open across the pointer's move into it, and never changes the strip's size. Hover makes no key/main or app-activation request. While the pointer is over the originating icon or open panel, temporary Carbon hotkeys accept Y, N, C and Escape without activating DevJay or changing key/main windows. A deliberate click can still give the panel keyboard focus. The buttons read Yes, No, Claude from left to right, with their first letters colored and underlined to identify shortcuts. C or the Claude button consumes the one-use token with a no-verdict fallback and routes its observed Site/host through the existing desktop/app activation handoff; no terminal keys or IDE commands are injected. It brings the host forward but cannot target an exact terminal tab. The hover hotkeys resolve Y/N/C against the current keyboard layout, include plain and Shift variants, and reserve only C/Escape for navigation-only popups. Mouse movement unregisters them outside the exact icon/panel rectangles; the existing timer is a fallback. Delivery rechecks the pointer, origin visibility/Space, current token and registration generation. Y approves the displayed request immediately. Yes/No disables response controls and releases hover shortcuts immediately, sends the callback, then pulses the selected button for one second before dismissal. Request removal and pointer exit do not interrupt this visual feedback; closing or leaving the originating desktop still cleans it up. A cancelled feedback timer cannot close a later popup. Navigation remains immediate. Initially held keys and repeated presses are ignored. Return, keypad Enter, Space and other keys are never registered, so they stay with the focused app. A registration conflict rolls back the entire set and offers click-to-focus fallback. Mouse monitors exist only while the panel is open; no global keyboard event monitor or event tap is installed. A local key monitor retains focused-panel support, including selected preview text, and modified shortcuts pass through. Response buttons suppress AppKit’s implicit Space/Return activation even when deliberately focused; only the advertised mnemonics or explicit clicks respond. Escape dismisses, repeated keys are ignored, and answered requests cannot be replaced beneath a stationary pointer. Closing, desktop changes, sleep and app activation clear the popover. A 150 ms tolerant timer exists only while the popover is visible to manage pointer exit and parent visibility.

Initial settings installation is explicit and Settings-sender-only. At startup, a background read upgrades only this executable’s already-enabled hook with the legacy 310-second timeout to match the 24-hour bridge lifetime plus ten seconds. It never enables an absent hook or changes another executable’s handler, custom timeout, or other hook fields. The same backup/concurrent-change checks apply. The observed global enabled state supplies accurate fallback guidance. It reads owned regular settings files without following symlinks, preserves unknown JSON fields including large numbers, backs up existing bytes and atomically replaces the file after a concurrent-change check. It updates only the recognizable DevJay hook, preserving other hooks and all permission rules. Enabling a different app path replaces a previous DevJay handler; disabling an old copy cannot remove another copy's handler. ## Application updates

`updater.go` implements version comparison, bounded HTTPS release checks/downloads and staged bundle verification; `updater_darwin.go` routes UI requests through the manager queue. Installed, versioned builds check three seconds after launch and every six hours, with a manual Help menu check. Development and unversioned builds never check or replace themselves. The feed is the fixed DevJay GitHub releases endpoint; tests inject a local HTTP client/server directly without a production feed override.

The strip and Settings share snapshot state for checking, available, downloading, ready, installing, manual-install and error states. Only the registered strip/Settings senders can request updater actions, and downloads/restarts require separate user clicks. One operation runs at a time. Download/verification work runs off the manager queue, reports integer progress, enforces transfer/archive-size limits and rejects unexpected or traversing archive paths and symlinks. SHA-256, code signature, bundle identifier and release version must match before offering restart. Disk-image/translocated or unwritable installations receive a manual-download action instead.

Staging uses a private temporary directory alongside the installed app so replacement stays on the same volume. Restart starts the embedded helper with positional arguments and then requests normal application quit, whose lifecycle gate waits for every confirmed Git mutation. The helper waits for the old PID to exit, rechecks the staged bundle, renames the old app to a recovery location, moves the new bundle into place, and launches it. Failed swaps restore and reopen the previous app; logs and recovery files remain in the staging directory on failure. A normal quit without installing removes a ready staged update. Settings and the development bundle are never migration targets. Certificate-backed Gatekeeper behavior and updates between real published releases still require live validation.
