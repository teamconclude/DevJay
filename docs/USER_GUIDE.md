# DevJay user guide

See the [README](../README.md) for installation and first steps. This reference covers everyday controls, Git actions, and recovery.

## Profiles and Settings pages

Settings has an icon sidebar: **Sites**, **Profiles**, **IDEs & editors**, **Windows and layout**, and **Keyboard shortcuts**. Sites is the initial page; Settings remembers the last page during the session. Command-comma opens it; Done, Escape, or the close button dismisses it.

A **Profile** remembers a monitor combination, enabled Sites, card order/layout, window decorations, editor/app preferences, and DevJay window positions and desktops. If no Profile exists, DevJay adopts the existing arrangement into a Profile named **Default**. Rename it to **Office**, **Home**, or **Laptop** in Settings → Profiles.

Choose **New profile** at the top of the Profiles page to enter its name in a dialog. **Manage profiles** lists each Profile with **Rename** and **Delete** actions. Deletion requires confirmation and removes that Profile's settings and saved arrangement, while keeping your Sites and folders. Switch to another Profile before deleting the active one.

DevJay recognizes connected display identities after a brief settling period. With automatic switching enabled, reconnecting a known combination restores its Profile. An unfamiliar combination prompts you to create a Profile or choose an existing one. **Not now** keeps saved arrangements protected; **Use with these displays** associates the selected Profile with that combination. Creating a Profile starts with the current Sites and preferences and saves its window arrangement separately. A Profile can recognize more than one combination, but each combination selects only one Profile. DevJay does not use your geographic location.

On the Sites, IDEs & editors, and Windows and layout pages, **Apply changes to** defaults to the current Profile. Expand it to choose **All Profiles** or individual Profiles before editing. Only the settings you change are copied; unrelated preferences and native window positions remain independent. Closing Settings resets this selection to the current Profile. Unchecking a Site hides it in the selected Profiles without unregistering it. The **×** removes it from every Profile after confirmation.

New Sites are registered in every Profile. **Add new Sites after** chooses their neighbor in card order; each Profile retains its other Sites' relative order. DevJay attempts the next desktop number on that Profile's corresponding display without displacing an existing Site. If that desktop is missing, occupied, or cannot be identified, Settings shows **Choose a desktop, then Keep here**. Move the Site using Mission Control, then choose **Keep here**. DevJay does not create macOS desktops or rearrange other applications' windows.

Saved layouts are protected while displays disconnect or an unknown combination is waiting for a Profile. Visible DevJay windows that extend outside the available screens are moved back inside, and oversized windows are reduced to fit. Hidden and minimized Site windows stay hidden. The Profile prompt remains usable without blocking the strip and closes automatically when its monitor combination changes; Escape dismisses it. Restoration uses the available macOS desktop support; missing/deleted Spaces still require manual placement. Physical reconnect and sleep/wake behavior should be verified on each monitor arrangement before relying on it.

### Renamed, moved, or missing folders

DevJay records a macOS folder bookmark and checks it in the background, normally within about 15 seconds while awake. A recognized rename or move updates the path and card name while retaining the Site ID, window, desktop, card order, and Profile membership. If a rename would change name-sorted order, DevJay keeps the old order and switches that Profile to Manual sorting. A different folder appearing at the old path does not replace the original Site.

For a folder that was already missing before bookmarks were recorded, or a move macOS cannot resolve, use **Settings → Sites → Locate…** beside the Site. Select its new folder; the existing Site and arrangements are retained. The selected folder cannot already belong to another Site. Moving between volumes, unavailable volumes, and moves to Trash may need this manual recovery. Locate changes only DevJay's registration; it does not move files or repair Git worktree links.

## Sites and Settings

When a Site label is too wide, DevJay first shortens the beginning of its directory path, keeping the Site name intact (for example, `...xyz/longname`). If the name itself cannot fit, the directory is hidden and the middle of the name is shortened (for example, `extre...name`). The full path remains available on hover.

Open Settings and drop a folder from Finder into the Sites list. Any folder is accepted; Git clones and worktrees get branch/status information. Symlink aliases of an existing Site are rejected. Site registration never creates, deletes, or checks out a repository. The **×** beside a Site asks for confirmation, then unregisters it and closes its windows, leaving its folder unchanged.

**Window decoration** offers **None** (default, content only), **Minimal** (borderless with small controls on both the strip and Sites), and **Normal** (native macOS title bars). The choice applies immediately to the strip and all Sites and is saved between runs. Settings uses a normal macOS title bar, a resizable window, and scrolling pages. Escape and the native close button close it. Right-click anywhere on a card for a native context menu; its last two items are **DevJay settings…** and **Quit DevJay**. The **DevJay → Settings…** menu item and Command-comma also open Settings. Shift-F10 or the Context Menu key opens the menu for a focused card control. Hover tracking also works while DevJay is inactive, without taking focus from another app. Click a strip card, above or below the divider, to activate its Site. Settings, other controls, and selecting status text retain their own behavior. With Settings closed, drag that heading to move the whole strip. Drag an independent Site by its heading; the PR tag and status area do not move it. Place each Site window on its desired monitor and desktop using Mission Control. Choose **By name** to sort by directory name (case-insensitive, with the full path breaking ties), or **Manual** to use the saved custom order. Drag a row by its dotted handle to reorder; this switches to Manual. Keyboard users can focus the handle and press Up or Down. The selected order also controls the main strip.

Cards show a subdued parent path, bold directory name, branch, local edits, upstream comparison, and GitHub review state when available. Local edits are blue. Routine base-branch updates are subdued blue-gray, while cached/unavailable base information stays amber. Small pencil, fork-shaped branch and comment-bubble icons label Edits, Branch and Review; hover for their names. Reviews for multiple PRs retain their PR-number labels. The bent arrow (↳) marks a separate base-branch comparison: for example, “develop · 2 newer commits” means the tracked develop branch has two commits not included in the current branch. An approved or merged PR uses a green **#1234** tag; a CI failure or action-required check takes priority and keeps it red. A colored **#1234** tag appears in the upper-right corner for each associated PR, using the branch font size. A PR with failing CI has a red **× #1234** tag. Checks that need action use a red **!**; running or queued checks use **◷**, and cancelled checks use **⊘** in the normal PR color. Hover the tag for its CI and review status; clicking still opens that PR. Review approval does not override a CI failure. Cards without a PR omit both the tag and the old “No open PR” line. Hover a card for its full path, desktop, upstream, and last successful remote-check time. The strip can be resized and scrolls horizontally when needed. Cards show their full status content. The strip automatically grows and shrinks as status and app rows appear or disappear, leaving 12 points of extra room beyond the fitted content and keeping a minimum content height of 132 points. It waits 300 milliseconds before growing and three seconds before shrinking, so brief status messages do not make the strip jump. If the content returns to its previous height during that pause, the resize is cancelled. Its width and nearby bottom edge (otherwise the top edge) stay in place. Opening the strip or changing decorations or layout also refits its height. Independent Site windows grow when needed and retain their height when content becomes shorter. Minimal decoration adds only its small control row above the same compact cards; Normal uses the native title bar without an extra empty row. If the display cannot fit all content, scrolling is available in the outer window or card list.

The lower-left corner shows supported IDEs, terminals, and standalone Codex/ChatGPT and Claude apps with windows on the Site's desktop, including inactive desktops. Each app uses its installed Mac icon followed by smaller Claude Code and/or Codex icons inside one capsule when those agents are detected in that host. If at least one editor or terminal is paired with an agent, the card shows only the paired groups; otherwise it shows all detected apps as single icons. Rest the pointer inside a capsule or single icon for about half a second to see a short label such as **GoLand with Claude Code and Codex**. Gaps, row padding, and the rest of the card do not trigger the app-status popup. The popup works while DevJay is inactive, extends beyond the strip when needed, and does not take focus or intercept clicks. App groups wrap if needed, and missing icons use initials. The two agent marks are bundled; their desktop apps do not need to be installed. This observes desktop placement, not which folder or terminal tab an app is using, and does not change the preferred editor for opening files. **No app detected** means no supported window was found; **App unknown** means desktop detection is unavailable or still pending. Apps assigned to every desktop are excluded because they do not identify one Site. Detection uses window/process metadata and cached app icons, without reading window titles, terminal text, or screenshots and without requesting Accessibility or Screen Recording access. One background discovery pass covers all Sites, with a thirty-second safety interval and earlier checks after desktop/app or Site placement changes. Agent activity uses separate, lighter reads. Both pause while the display/session sleeps.

When local process evidence is available, the capsule adds **Claude Code** or **Codex** icons beside their host, with their names in the hover text. DevJay matches a recognized native agent process's working folder to the most specific Site folder and checks that its parent app has a window on that desktop. iTerm's separate persistent shell server is also recognized. This is best-effort presence: an app can have several windows or tabs, so the exact window/tab is not verified. Missing labels do not mean no agent is running: remote sessions, detached servers, script-only installations, inaccessible process metadata, and sessions outside the Site folder may be missed. Standalone AI app windows remain ordinary app labels. Process IDs and working directories are not persisted or sent to the card; environment variables and full command lines are not read.

An **amber capsule and a small ? on an agent icon** mean that agent reports waiting for input or approval. A newly detected wait sends two soft amber breaths from the center of the card over four seconds, with the second quieter than the first, then leaves the capsule amber. Ordinary status updates do not restart the pulse. The animation respects macOS Reduce Motion. Hover text identifies it, for example **GoLand with Claude Code and Codex · Claude Code needs input**. The marker clears on the next scan after work resumes or the process exits; known working/waiting sessions are normally checked every two seconds, and Claude registry changes can be picked up sooner. Multiple sessions in the same app group share one indicator, so any verified waiting session can mark that agent. The indicator never answers a question or switches desktops; clicking its card still performs ordinary Site navigation.

A **teal capsule with three gently moving dots and a small ▶ on an agent icon** mean a matched session reports that it is processing. Hover text names the working agent, for example **GoLand with Claude Code · Claude Code is working**. The three dots softly rise and fade in sequence in place of a text label; the app and agent icons stay steady. The dots disappear when working clears and add no polling. With macOS Reduce Motion enabled, the dots remain still. Claude's idle background shell tasks, such as a development server left running, do not count as processing. A waiting session takes priority over a working session of the same agent. When Claude and Codex have different states, their icons show their individual markers; the capsule stays amber and omits the working dots if either needs input. Known working/waiting sessions are normally checked every two seconds. Idle sessions are checked every twelve seconds, with earlier updates from Claude registry changes and a brief faster period after desktop/app activity. Working confirms an observed session's state; it does not establish that every session on that desktop is busy.

Working and waiting detection read Claude Code's small local process-status registry and, where available, the running Codex daemon's status for loaded CLI/IDE sessions. It installs no hooks, changes no agent configuration, requests no conversation history, and uses no OCR. This initial implementation uses the default `~/.claude` and `~/.codex` locations. Claude's registry format and Codex's local daemon interface can differ between versions. Standalone desktop apps, remote sessions, Codex sessions outside that daemon, missing metadata, and ambiguous folder/host associations have no activity indicator. A normal icon therefore means **no confirmed working or waiting signal**, not proof that the agent is idle or can continue unattended.

**Settings → IDEs & editors → Show development app status** controls this display and defaults to on, including for existing configurations. Turning it off hides the icons in the strip and Site windows and stops background app detection. The choice is saved across restarts. Turning it back on starts a fresh reading.

**Strip on all desktops** keeps the main window on ordinary desktops on its monitor; it does not duplicate it across monitors. **Show all windows on top** floats all DevJay windows. Both default to enabled, persist between runs, and remain available in the View menu. Settings is a separate window; closing it or pressing Escape leaves DevJay running.

The Sites menu provides Command-1 through Command-9 for the current card order, and Command-0 for DevJay. These remain app-local shortcuts. Command-Q quits DevJay when the app is active and saves the layout; the strip does not take keyboard focus, so app-local keyboard shortcuts stay with the previous app until you activate a Site or open Settings. The strip supports mouse controls, dragging, and context menus; use Site windows or Settings for keyboard interaction. The strip’s × button is available in Minimal decoration, and the native close button is available in Normal decoration. With any decoration, right-click a card and choose **Quit DevJay** to quit without needing keyboard focus. Remove Sites in Settings; Site windows have no close controls. Selecting a minimized Site restores it.

For navigation, enable System Settings → Desktop & Dock → Mission Control → **When switching to an application, switch to a Space with open windows for the application** if needed. Keep the app's Dock assignment at **None** so windows can occupy different Spaces. No Accessibility permission or editor integration is required.

## Minimized and hidden strip

Right-click any card or empty area of the strip and choose **Minimize strip** for a 40-point-high row of Site names, roughly the top fifth of a normal card. The names stay clickable, the current desktop keeps its blue highlight, and the row scrolls horizontally if all cards do not fit. It follows the current card order, including when the full strip uses a vertical or custom layout. Right-click the row for **Restore strip**, **Hide strip**, **Hide site windows** (or **Show site windows**), Settings or Quit.

Choose **Hide strip** to hide it completely. **⌃⌥⌘D** or **View → Show strip** restores its previous full or compact view. Hiding preserves the strip’s size, position, layout and decoration. Opening Settings, showing DevJay from the Dock, or relaunching restores the full strip. Minimize and Hide are separate from the **Minimal** window decoration setting.

**Hide site windows**, directly below **Hide strip** in the strip’s context menus, hides the independent Site windows and changes to **Show site windows** while they are hidden. **View → Hide Site windows** or **⌃⌥⌘S** also hides the independent Site windows without changing the strip. Use the same shortcut or **Show Site windows** to restore them without taking keyboard focus or selecting another desktop. The choice is saved across app restarts, virtual desktop switches and Profile changes. Clicking a Site card, using its shortcut or opening its app still switches to that desktop while keeping Site windows hidden. Only **Show site windows** or the visibility shortcut reveals them again. Layouts and existing minimized states are preserved, and new Sites follow the saved choice. DevJay stays running even when both Site windows and the strip are hidden, so the shortcuts can restore them.

These are the default shortcuts; they work while another app is active:

| Shortcut | Action |
| --- | --- |
| **⌃⌥⌘D** | Hide/show the strip, restoring its previous full or compact view |
| **⌃⌥⌘S** | Hide/show independent Site windows |
| **⌃⌥⌘M** | Toggle the compact row; restore the full strip if hidden |
| **⌃⌥⌘1–9** | Visit the corresponding Site’s desktop, in current card order |
| **⌃⌥⌘0** | Restore and show the full strip |

Open **Settings → Keyboard shortcuts** for a list of actions and their current combinations. Choose **Record** beside an action, press a key with Control, Option or Command (and optionally Shift), then release the key. A valid combination takes effect immediately and is saved across launches for all Profiles. Escape, clicking elsewhere, leaving Settings, or waiting thirty seconds cancels recording. Global shortcuts are temporarily suspended while recording so the combination does not trigger another DevJay action. Duplicate assignments, reserved DevJay menu shortcuts and combinations macOS cannot register are rejected; a registration or save failure keeps the previous assignments. **Reset** restores one default, **Restore defaults** restores all, and **Retry unavailable shortcuts** retries registration after a conflicting app releases a shortcut.

Hold a Site shortcut’s modifiers to show its assigned key on the full or minimized card, then press that key to visit the Site. Defaults use **Control–Option–Command** and the number-row 1–9 keys. A hidden strip stays completely hidden while modifiers are held. Releasing the modifiers removes the hints; merely holding them never switches desktops or changes the strip mode. Unavailable bindings and Sites beyond the ninth have no badge. Site numbers follow sorting and manual reordering; unused numbers do nothing. Visiting a Site keeps the minimized or hidden mode in place. Shortcuts use physical key positions, displayed with their US key labels, and require no Accessibility permission. Standard app-local menu shortcuts are listed separately and retain their bindings.

## Strip layouts

Settings offers **Horizontal** (default), **Vertical**, and **Custom**. Custom initially wraps cards into tiles as the window is resized. Only while Settings is open, drag a card by its heading: Horizontal and Vertical reorder the cards; Custom saves free positions on an invisible 8-pixel grid and allows overlap. Moving a card brings it above overlapping cards. **Reset card positions** in Settings returns Custom to automatic tiling. Layout and custom positions survive restarts. Dragging while Settings is open switches sorting to Manual. Status text remains selectable for copying; drag the strip background to move the window while rearranging cards.

## Card clicks and context menus

When a context menu offers a suggested Git action, it appears first, followed by the clicked control's ordinary action. Edit counts offer **View changes**; commit counts offer **View branch history**. The corresponding **in new window** option appears only when that Site already has a Changes/History window open, including one showing a different category. **Edits**, **Branch**, and **Review** are plain text headings; their counts remain clickable. PR tags and review statuses/counts offer **Open PR #1234 in browser**, then **Open PR #1234 in new browser tab**. App icons and their nested agent icons offer **Show GoLand**, **Show Visual Studio Code**, or the observed app's name; selecting it performs the same action as clicking the icon. Card background menus offer **Go to Site desktop** after any suggested Git action. Settings and Quit remain at the bottom.

Card and branch menus also suggest one relevant Git action. Incoming counts offer **Fetch and update <branch>…**; outgoing counts offer **Push N commits…**. Other card areas prefer returning after a merged PR, replacing verified rewritten remote history, publishing a recognized rebase, updating incoming work, or rebasing onto a newer default branch before an ordinary push. When the local tip is verified as a previously published upstream tip, these menus offer **Replace from remote…**, using the same checks, recovery copy, and separate confirmation as the Changes window. If a rebase is blocked but a push is available, the menu offers the push. Right-click the outgoing count to push existing commits without first rebasing onto a newer default branch. Known unsafe updates are disabled with a reason: local edits must be committed or stashed manually, and diverged or rewritten histories require review. An ordinary push allows local edits. Every enabled Git action opens the existing safety review and requires a separate confirmation; opening the menu changes nothing. Untracked comparisons do not authorize updates or pushes.

Folder and branch names are the exception: clicking keeps the existing Site/desktop navigation, without automatically activating an editor or terminal. Their context menu offers **View changes** when local edits or conflicts exist, otherwise **View branch history**. If local status is unavailable, Changes remains the inspection entry point. The card still labels local work **Edits** and **N edits**.

Right-click **develop · N newer commits** and choose **Rebase and push…**. This uses the repository's default branch, such as main or master. DevJay checks the complete rebase and verifies that remote work will be preserved before offering one confirmation for both operations. The compact window shows **Safe to continue** only after these checks pass. Conflicts or unverified cases show **Manual action needed**, with guidance to use Claude or Astra and technical information under **Details**. Known blockers disable the menu item with an explanation.

Windows opened from strip cards appear above the clicked card, horizontally centered on it. If there is no room above but the window fits below, it opens below instead. Changes/History windows opened from an independent Site window appear centered over it. Confirmations from Site or Changes/History windows also overlay their parent. **Switch...** opens the branch chooser vertically centered over the Changes/History window, just to the right of the Switch button; branch selection and Back keep that placement. All placements keep the dialog within the usable screen area.

After a rebase, the independent Site window also shows **Push rebased branch…** below its Git status. Clicking it starts the same checks and separate confirmation as the context-menu action. It is disabled while another Git action is being checked or applied, or while local edits, conflicts, or unavailable branch information need attention. Its context menu puts the push action first. The strip keeps its compact status layout.

Clicking an IDE/agent group, a standalone app icon, or its **Show** menu action first switches to the Site’s desktop, then focuses the already-running app. DevJay waits for that desktop to become active before handing over focus. Another navigation request or a change of focus cancels a pending handoff. This does not launch an app or open a project, file, or terminal tab; macOS and the app choose the existing window. An unknown, vanished, or ambiguous app identity is rejected. Background app observation and hover remain passive.

## Inspect changes

Card status texts highlight on hover, even in inactive windows. Click **In sync**, another Git status, or a card’s **edits**, **not pushed**, or **incoming** count to open a read-only changes window, from either the strip or an independent Site. The **Changes** tab lists each changed path once, sorted by path, with its staged, working-tree, or untracked status. A file with both staged and unstaged edits stays in one row; choose **Staged** or **Working tree** above its diff to inspect the corresponding changes. These controls only change the diff being viewed. Select a file to see its diff, with line numbers and colored additions and deletions. Choose **Unified** or **Side by side** above the diff. The repository and current branch appear in the top toolbar, alongside available push/update actions that follow the current checkout. Up to three direct action buttons appear, with the recommended action on the right and secondary choices subdued. Status and warning text stays between **Switch...** and the action buttons. It uses one line when it fits and wraps to at most two lines in the same space when needed; hover a truncated message to read it in full. The warning never moves to a separate toolbar row. Local-edit guidance names the operation it blocks, such as rebasing or updating; ordinary pushes remain available with local edits. Clicking an action such as **Push 3 commits** starts safety checks and opens **Confirm push**; a separate confirmation is required to apply it. Opening a viewer never changes the checkout. Clicking another category reuses that Site’s existing changes window and selects the category. Right-click a count or status to view that category; if the Site already has a Changes/History window, the menu also offers a new independent window. If several windows exist, DevJay prefers one already on the requested category, then the most recently used. Each window keeps its own selected commit, file, and snapshot. Opening Changes/History from a strip card positions it above that card, horizontally centered, with a below-card fallback and screen-edge clamping. Other viewers do not move it away from the card. Opening from an independent Site window centers it over that window. These rules also apply when reusing an existing viewer; background refresh leaves its position alone. The file summary shows the number of unique paths and total added/removed lines. The overall count includes each path once; line totals sum staged and unstaged changes separately. Binary changes are excluded from line counts, and unavailable or limited counts are labeled partial. The viewer does not stage, commit, or change files.

Use **↑/↓** to select commits or files and show their diffs. **Home/End** selects the first/last entry in the current list (within the current history page). **Tab/Shift-Tab** moves between lists and controls; **↓** from Changes or History enters its list. The active row uses the usual selection highlight, without an outline around the list, and stays in view as you navigate. The list and surrounding controls remain steady while the selected diff loads. Arrow keys scroll normally when the diff has focus.

Select a file and click **Open in GoLand** (or your chosen editor) beside its diff. In **Settings → Editor**, choose one preferred editor for all Sites. Enable **Automatically use the editor with this project open** to prefer a detected project editor, falling back to your preferred editor when no unique match is available. Installed editors and **Choose another application…** are available there. Project detection recognizes a running JetBrains IDE reporting that exact checkout open, using its optional discovery metadata and verifying the live application. If detection is disabled, DevJay always uses the preferred editor. macOS asks the existing application to open the file; project-window routing is handled by that editor and is best effort. No Accessibility permission is needed. Opening always uses the current working-tree file, even while viewing an older commit. Deleted files and links outside the checkout cannot be opened from the viewer.

The **History** tab defaults to **Branch history** whenever you open it, including when returning from **Changes** or reopening the viewer from a card. The list shows only commits added since the branch’s common ancestor with the cached remote default branch, including published branch commits and excluding shared ancestors and remote-only commits. On the default branch itself, the comparison uses its cached upstream. The heading shows the branch commit count and names the base. A branch with no added commits shows an empty list. If no base is available, an explanation appears and **Full history** remains available.

Use the **Branch history / Full history** switch above the list to choose its scope independently of opening the combined diff. **Full history** includes the branch’s complete history and its last fetched upstream, in pages of 100; without a remote comparison, it shows local history. Switching scopes selects the first commit. Selecting commits, paging and refreshing preserve the chosen scope. Compact commit rows show the subject, author, date and short revision in Git history order. Dates stay on individual rows because rebased commits can retain older author dates. Commits absent from the upstream are marked **Not pushed** with a blue dot; remote-only commits in Full history are subdued with an outlined dot and an **Incoming** label. Shared commits appear once without repeated badges; their presence remains available in the tooltip and selected-commit details. The selected commit’s summary spans the detail area above its file list and diff. Incoming commits have already been fetched for inspection; **Update <branch>** fetches again and, after confirmation, includes them in the local branch. These markers compare commit IDs, so rebased equivalents remain distinct. Select a commit, then a file, to inspect its changes. Merge commits are compared with their first parent. For **Rebased · ready to publish**, choose **Full history** to inspect both sides of a rewrite. **Changes** remains a separate tab for uncommitted files.

In **History**, choose **All branch changes** to open a side-by-side comparison of the committed branch tip against that common ancestor. This includes already-pushed branch work and excludes uncommitted edits and changes made only on the default branch. The comparison names its base; if no unique common ancestor or cached base is available, the option is disabled with an explanation. Opening it also selects **Branch history**, so the list and combined diff cover the same range. Select a commit to inspect it individually, or choose **All branch changes** again to return to the combined diff. In side-by-side mode, files appear below the commits, leaving the rest of the window for aligned before/after panes. Insertions and deletions have blank counterparts, and changed portions of paired lines are highlighted. Long lines wrap while both versions stay vertically aligned. The layout choice stays with that viewer until it closes.

Use **↑ / ↓** in the diff toolbar for the previous/next difference in the current file, and **← / →** for the previous/next file. **Option+Up/Down** and **Option+Left/Right** do the same from within the viewer. The counters show the current difference and file, and controls stop at each end of the list. File navigation follows the displayed file order and counts staged/working versions of one path as one file. Use the existing **Staged / Working tree** controls to switch between those versions. Binary or metadata-only changes have no textual differences to navigate; combined conflict diffs stay in unified form. Existing file and diff display limits still apply, and the viewer remains read-only.

When both local and remote have different commits, the card and History window say **History differs**, **Local only**, and **Remote only**. These are commit-ID differences; remote-only entries may be older versions after a rebase, rather than new incoming work. For feature branches, commits already present on the cached remote default branch are excluded from the displayed local-only count. The tooltip explains the excluded count, and inherited History rows name that default branch. This display does not establish rebase or push safety: unverified histories still require manual review with Claude or Astra, and publication checks remain unchanged. If the default-branch comparison cannot be read, the full local-only count remains visible.

For a branch without an upstream, incoming/outgoing counts and **Full history** use the cached same-name branch on `origin`, or `origin`'s default branch when no same-name branch is available. The viewer names this comparison and labels it **No upstream configured; cached comparison**. For example, an unpublished branch with three commits beyond `origin/main` shows three **Local only** commits alongside the shared history of `origin/main` in **Full history**; **Branch history** lists just those three branch commits. This comparison does not configure tracking or enable a push; publishing a new branch remains manual. If neither comparison is available, counts remain unavailable rather than showing zero.

Visible Changes windows reread local Git data every 10 seconds after the previous refresh finishes, and sooner when the Site’s Git status changes. Hidden windows pause automatic reads and refresh when shown again. This also catches edits whose file count stays the same. Automatic refresh keeps the current file or commit when possible, including following commits onto another history page. It preserves scroll position for the same diff and leaves unchanged diff text in place for copying. If the selection disappears, the first available entry is selected; a note explains when the previous commit could not be located. Branch changes reset the selection. **Refresh** remains available for an immediate reread. Each displayed comparison uses a consistent set of captured revisions until the next refresh. Remote fetches remain on the separate background monitoring schedule. Binary files show a notice, and large file lists and diffs have explicit display limits. Escape or the native close button closes the viewer.

## Open pull requests

Click a card’s PR tag (or its review status) to reuse an existing tab showing that PR. DevJay checks running **Safari, Google Chrome, Microsoft Edge, and Brave** windows only when you request a PR action. A tab showing the PR’s Files, Commits, or discussion page counts as the same PR. It selects that tab and activates its browser window; switching macOS desktops depends on the browser and Mission Control settings.

Right-click the tag for **Open PR #1234 in browser** and **Open PR #1234 in new browser tab**, followed by **DevJay settings…** and **Quit DevJay**. A new tab prefers an existing window that already contains GitHub PR tabs, then a window in the supported default browser. If no suitable window exists, DevJay opens the URL in the default browser, whose preferences determine tab versus window placement.

macOS may request **Automation** permission for each running supported browser. Access can be managed in **System Settings → Privacy & Security → Automation**. If inspection is denied or unsupported, DevJay falls back to ordinary URL opening; it cannot promise reuse in that case. Tab URLs are inspected only for this action, never stored or polled in the background; page contents are not read. No Accessibility permission or “JavaScript from Apple Events” setting is required.

PR-opening failures appear in a native message dialog above the originating card (below it if needed), or centered over an independent Site window. The dialog stays on the available screen and remains visible until dismissed with **OK** or Escape; it does not change the strip height. Clicking a review warning or blocker opens its PR in the browser.

## Git monitoring

### Switch branches from the Changes window

Open the Site’s Changes window by clicking its status or change count, then click **Switch...** beside the branch name. Choose a branch and review the separate confirmation. Branch names on the small desktop Site card and strip remain labels. The wider, taller chooser shows at least six branch rows, with PR numbers, review status and CI status on a second line. Search matches branch names and PR numbers. Open PR details load on demand after the branches appear, and reopening refreshes them. Offline or incomplete GitHub results are labeled explicitly; branches without a linked remote show that instead. The chooser lists local branches and locally known remote branches; it does not fetch every remote branch in the background. To discover a newly created remote branch that has never been fetched locally, fetch it with your Git tool first, then reopen the chooser.

DevJay requires a clean checkout before switching. With local edits, the switch dialog suggests stashing unfinished work in your Git client, or committing it if ready, before trying again. Commit or stash staged, unstaged, or untracked work yourself first; DevJay never stashes, restores, discards, or overwrites it for you. A branch checked out in another worktree cannot be selected safely. Incoming collisions with ignored files also stop the operation. The original branch is kept.

Selecting an existing local branch checks its upstream when available. If the remote contains newer commits and every local commit is already included there, the confirmation offers **Use newer remote version**. Choosing that option prepares a new plan; confirming it switches and fast-forwards to the checked remote commit. If the local branch has unpublished commits or has diverged, DevJay keeps the local version and does not offer that update. An unavailable remote check is labeled, while switching to the existing local version remains possible. Selecting a remote-only branch creates a local tracking branch after confirmation. Changes to the checkout or destination after preparation stop the action and require another review.

### Background status and suggested actions

Local status follows filesystem changes, grouping rapid saves into a single check after roughly half a second. Continuous edits trigger a check within about two seconds, plus the time Git needs to read the repository. Quiet folders use a two-minute safety check; switching to a Site requests a fresh reading. Local commands have four reserved slots, separate from the two network-command slots. Failed local readings preserve the last complete status and PR findings with an explicit cached-status warning, without forgetting the upstream or retry schedule.

Moving the pointer over DevJay, clicking, scrolling, typing in its windows, using a DevJay global shortcut or menu command, or reopening the app selects the active PR-status cadence across all enabled Sites:

| Time since the last interaction | Current desktop | Other desktops |
| --- | --- | --- |
| Less than 2 minutes: active | 10 seconds | 15 seconds |
| 2–10 minutes: normal | 1 minute | 2 minutes |
| 10 minutes or more: background | 2 minutes | 5 minutes |

Both inactivity thresholds are measured from the last interaction. New input returns immediately to active cadence and requests overdue checks. Pending CI follows the same schedule. Fast PR checks use a lightweight query; full remote checks and detailed review reports run once a minute during active use, then follow the normal/background intervals above. Failed GitHub queries retry no faster than once a minute, or at the selected cadence if slower. Intervals are measured after completion, so slow connections or queued work can add time. Before any interaction is recorded, startup uses background cadence after the initial refresh.

Normal time between successful checks is not a failure and does not display a stale warning. Hover a card to see the last successful remote-check time. A failed check explicitly says **Remote check failed · showing last check**; an initial pending check says **Remote not checked**. Display sleep and session lock pause background monitoring; waking requests fresh state. Hidden windows stop their working animations and defer rendering until shown. Status distinguishes no upstream, detached HEAD, an empty repository, local changes, merge conflicts, ahead, behind, diverged, and a removed upstream branch. Non-Git and unavailable folders remain usable Sites with an explanatory status.

Automatic monitoring fetches the configured upstream and the remote default branch into their remote-tracking refs, with tags, submodule recursion, maintenance, and configured extra ref mappings disabled. Monitoring never changes checked-out files or local branches. Offline/authentication failures retain cached comparisons and label them explicitly; they are never represented as a fresh “Up to date.” When a feature branch has moved onto a newer default-branch base and every remote-only commit has an equivalent local patch, the card shows **Rebased · ready to publish** instead of misleading incoming/outgoing counts. Commit counts remain in the tooltip. Unverified remote status is labeled explicitly; genuinely new remote patches or unverified merge commits retain normal divergence warnings. The rebased status offers a separately confirmed publish action with stronger conflict and history checks; DevJay does not suggest pulling the old history. A non-fast-forward change to the observed remote-tracking ref is flagged as rewritten history when the local and remote branches have diverged, or their relationship is unavailable. If the remote still contains every local commit, an amended incoming commit remains an ordinary incoming update; it does not show **Rewritten** or block a fast-forward. Verified replacement of an affected former upstream tip still retains the warning. Rewrites that occurred before the first observation or were fetched by another tool between checks cannot always be identified.

Suggested actions appear in a Site’s changes window when its checkout is at the exact tip of a merged PR, has local commits ahead of origin, has incoming upstream commits, or is missing commits from the remote default branch. Click a card's status to open these actions in the changes window; the **Switch...** button in that same Changes window opens the branch chooser. Return-to-default suggestions require an exact repository, branch-name, and merged-tip match with no staged, unstaged, or untracked edits. Reusing a previously merged branch name does not qualify. Click the specific action to fetch and check the exact source and destination commits, then explicitly confirm **Update branch**, **Return to the default branch**, **Rebase and push**, **Push commits**, or **Push rebased branch**. Confirmations expire after five minutes and cannot be reused. Cancel, ×, and Escape discard pending confirmation. Merged cards explicitly show **PR merged**. Right-click the card or its PR tag and choose **Return to develop & delete branch…** (using the repository’s actual default branch) to review both operations. The PR tag’s first menu action still opens the PR in a browser. Cleanup requires a clean checkout and an exact merged-tip match, works even after the remote feature branch is removed, and keeps a recovery reference. Local branch deletion is preselected for this menu action and remains optional in the confirmation; changing that option repeats the safety checks. Once an operation is applying, closing waits until it finishes. Quitting keeps the app responsive while waiting for all confirmed actions. Network commands have individual timeouts; local checkout mutations are allowed to finish.

Each Site has its own action dialog, so you can prepare and confirm operations for several Sites in parallel. A Site accepts one operation at a time. Independent repositories can apply changes concurrently; linked worktrees sharing a repository retain a common lock, so a conflicting action stops for review. Every operation still needs its own confirmation. Quitting waits for all confirmed operations to finish.

After a successful operation, a checked **Auto closing in 5 seconds.** checkbox appears to the left of **Done**. Uncheck it or press **Esc** to stop the countdown and show **Auto closing stopped.** Checking it again starts a fresh five-second countdown. Click **Done** to close the dialog immediately. Status refreshes do not restart a stopped countdown. Failed operations stay open for review.

- **Update <branch>** fetches again and only fast-forwards a clean checkout to its confirmed upstream commit, including `main`, `master`, and `develop`. An earlier remote-check failure does not disable this retry; a failed fetch still prevents an update. Ordinary divergence requires manual handling; verified rewritten upstream history may qualify for **Replace from remote**, described below.
- Returning after a merge switches to the repository’s default branch and fast-forwards it, creating it with remote tracking if absent. Both returning and optional deletion require the old branch tip to match a PR merged into that default branch. Deletion happens only after a successful switch and update; another worktree using the branch blocks it.
- **Rebase and push** tests the entire rebase in a disposable repository against the latest fetched default branch. It requires a clean checkout, an existing same-name origin upstream, and a verified linear history of at most 256 commits; merge histories need manual handling. Conflicts show the files at the first stop and require manual rebase and push with Claude or Astra. One confirmation authorizes both operations. DevJay repeats the trial, installs only its conflict-free result using your Git committer identity, and pushes the checked commit with a lease tied to the exact verified remote tip. A changed remote stops publication even if another tool fetched it in the meantime. If the server rejects the push, the completed local rebase stays in place with recovery copies of both original tips; finish manually rather than retrying blindly. The original branch moves with an expected-old-commit check, and no rebase is left in progress in the Site. No repository hooks, custom merge drivers, filters, or saved conflict resolutions run in the trial; union merge resolution is also refused. Repositories requiring signed commits must be rebased manually.
- DevJay retains recovery refs for the ten most recent verified successful checkout actions. Failed or partial actions keep their backups. Backups made by older versions are also retained because their outcome cannot be established safely. These refs are local, but Git mirror pushes can publish them; review refs before using `git push --mirror`.

A normal push is suggested for local-only commits with an existing same-name origin upstream. Review fetches origin and verifies that its tip is an ancestor of the local branch; confirmation pins the source commit and destination, rechecks both, and pushes only that branch without force or tags. Different/multiple push URLs require a manual push. Staged, unstaged, and untracked edits are allowed before and during a push; they stay on your computer, and the index and working files are untouched. Remote changes, divergence, changed branch/HEAD, conflicts, and unfinished Git operations stop the action. Edits made while the push is in flight do not turn a verified remote success into a failure. The result is checked against the remote even after a command error or timeout, with no automatic retry. Rebased publication uses the separate guarded action below.

**Push rebased branch…** is available by right-clicking **Rebased · ready to publish**, and in the Changes window. It requires a clean checkout and an existing same-name origin upstream. Before offering confirmation, DevJay fetches the branch and default branch, reproduces the remote rebase in a disposable repository, and requires every resulting tree, author and commit message to match the start of the local rebased history. Additional local commits may follow that verified series. The local branch must already include the checked latest default commit. Conflicts, changed remote work, ambiguous or merge histories, histories above 256 commits, and other unverified cases stop the action and require manual work with Claude or Astra. Confirmation repeats the checks, preserves the old remote tip in a local recovery reference, and pushes only the confirmed commit using an explicit `--force-with-lease=<branch>:<checked-remote-commit>`. Background fetches cannot weaken that lease. The push result is checked without automatic retries. These publication backups are retained without automatic pruning. Git conflict checks apply to the verified commits; they do not establish application correctness or predict future changes to the default branch.

Actions recheck checkout identity, HEAD, branch, remote, and Git operation state. Actions that change the checkout require clean index/files and refuse staged/unstaged/untracked work; an ordinary push allows those edits. All actions still refuse conflicts, hidden index flags, sparse checkouts, and submodules. Git’s no-overwrite-ignore behavior protects incoming collisions with ignored files. Actions are serialized per common Git directory; they cannot provide atomic protection against arbitrary concurrent writes by other tools or unsaved editor buffers. No automatic stash/pop, destructive reset, clean, or unconfirmed push is performed. Errors report the observed checkout state rather than attempting a blind rollback. If an external change interrupts the rebase’s branch reattachment, the message explicitly explains the detached checkout and manual next step.

**Replace from remote** is offered for a clean branch whose exact local tip appears among the last 256 recorded tips of its same-named upstream, and is no longer an ancestor of that upstream. This handles force-pushed history, including rewritten merges and multiple remote rewrites. It does not infer safety from commit dates, messages, or similar patches. Missing or expired reflog evidence, local commits beyond the recorded tip, edits, untracked files, hidden index flags, or another worktree using the branch stop the action. Preparation fetches the upstream; confirmation rechecks the local state, evidence, and exact remote tip. A recovery reference retains the old commits before the branch is moved to the confirmed remote commit, preserving its name and tracking. No forced checkout, destructive reset, or remote push is used. If interrupted after detaching, the result explains how to finish manually. Changes made concurrently by other Git clients cannot be locked out entirely.

Before updating, replacing, rebasing, or switching a local branch, DevJay preserves the original commits at **refs/devjay/backups/<action-id>**. The result window displays that reference. List retained recovery points with `git for-each-ref refs/devjay/backups/`; create a separate recovery branch with `git branch recovered-work <recovery-ref>`. These references survive restart; retention follows the ten-successful-actions policy described above, while failed, partial, and legacy backups remain available. They preserve commits, not uncommitted or ignored files.


PR and CI lookups use the configured remote upstream branch name, even when the local branch has been renamed. Without a remote upstream (including a local-only upstream), cards retain the same-name lookup on origin; this does not establish tracking or enable an action. Changing the remote URL discards previous remote status and requests a fresh check.

A small GitHub profile avatar at the bottom-right of a card identifies a PR authored by someone other than the GitHub account signed in through `gh`. Hover for the username and PR number, or click to open that PR. Multiple PRs can have separate avatars. Your own PRs and unknown authors have no avatar; if a known author’s image cannot load, initials appear in the same space. This works in the strip and independent Site windows, including when Development app status is disabled.

For GitHub.com remotes, `gh pr list` supplies open PR number, draft state, review decision, and checks for the latest pushed PR commit. PR approval and CI status follow the activity-based schedule above, including completed checks and branches with no open PR. Fast queries avoid fetching Git or rereading review discussions; normal and background updates come from the full refresh. CI describes the pushed PR commit, not unpushed local changes. A reported failure stays visible even while other checks are running. Missing or incomplete results are never described as passed, and skipped/neutral checks are distinguished from a passing run. DevJay also reads all pages of submitted reviews and PR discussion comments, showing blocker and warning counts from the latest recognizable report. Red ⊗ icons mark blockers, and amber warning triangles mark warnings. It accepts explicit `<!-- review blockers=1 warnings=7 ... -->` metadata or Markdown Blockers/Warnings sections with top-level list items (or “None”). Counts are reported findings, not an inferred GitHub approval decision. GitHub approval takes precedence over “No findings” and stays visible alongside any reported warnings or blockers; the tooltip retains the report date and URL. Changes to the pushed PR head, title, or description after the latest report show the historical review counts in light gray. These counts do not establish whether the latest commits still have those findings. Hover for the reason: **Commits changed since review**, **PR title changed since review**, or **PR description changed since review** (combined when several changed). Clicking a count still opens the PR. A new report for the current PR contents restores the normal review colors. Short reviewed commit IDs are matched to GitHub’s full IDs. Commit identity detects branch changes; title events and description edit timestamps detect PR edits. Labels, draft-state changes, references from other branches or PRs, and ordinary discussion do not mark the report outdated. Local edits and unpushed commits are shown separately on the card. If freshness cannot be checked, findings remain visible with **Review freshness unavailable**; unavailable posts are labeled **Review unavailable**. When no open PR exists, DevJay checks the latest 20 merged PRs for the same repository and branch. Only a checkout at the merged PR’s exact tip can show **PR merged** with **Branch left over after merge** underneath. A different tip has no association with the old PR. When the local reflog retains the branch’s creation record, a creation date after the merge also rules out the old PR, even at the same commit. Recreating a branch invalidates its cached GitHub status. If creation history is unavailable or expired, DevJay requires the exact tip and never infers a relationship from the name or shared ancestry alone. Local edits remain visible, and this is not a claim that deleting the branch is safe. Default branches do not show this leftover status. Dismissed and pending reviews are excluded. Ordinary discussion does not replace a report, and findings are not summed across repeated reviews. Missing CLI/authentication or network failures show **GitHub unavailable**. This version does not track individual unread comments or provide a review inbox. GitHub Enterprise and fork PRs targeting another repository are not resolved yet. Commands have bounded duration, output, and concurrency; interactive authentication prompts are disabled.

## Persistence and desktop APIs

Sites and custom order are stored atomically in `~/Library/Application Support/DevJay/sites.json`. A malformed configuration is reported and never silently overwritten. Window positions, display identity, desktop UUID, and appearance preferences are stored in macOS preferences under the `io.teamconclude.devjay` bundle identifier. Development and installed builds now use this same file and preferences domain. Only one copy can run at a time. Earlier development builds used `DevJay Development/sites.json` and `io.teamconclude.devjay.development`; those legacy files are left intact. To move an existing development setup over, quit both copies and back up both configurations before copying the development Sites file and DevJay layout preferences into the shared locations. Each folder has a stable identifier, so removing and re-adding it recovers its previous placement.

The strip remembers its width and position. Its height follows the cards automatically, including after status updates, resizing, and decoration or layout changes. Windows within 10% of the usable screen width or height of the nearer right or bottom edge preserve their gap in points when the resolution changes. Restored windows are clamped 8 points inside the usable display area. Missing displays fall back to the nearest available screen. Desktop identification and restoration use runtime-loaded private SkyLight APIs. Failed restores preserve the saved desktop assignment until the Site is moved; removed desktops or unavailable APIs leave windows accessible. These undocumented APIs may change with macOS updates. The main window skips desktop restoration when shown on all desktops.

## Recovering blank windows

After display/system wake or returning to the login session, DevJay reloads its web views once the display has settled. WebContent process termination also triggers recovery if WebKit's own reload does not restore a rendered snapshot. Reloads preserve native window positions, visibility, and backend Git operations; they do not repeat or confirm an action. Transient UI state such as text selection and scroll position may reset.

Recovery waits for fresh frontend state and retries at most three times per incident, with a rate limit for repeated crashes. Regular snapshots are paused while the display or session sleeps. If windows remain blank, use **View → Reload windows** to retry without quitting. Recovery events are logged with the prefix `UI recovery:`. A persistent macOS GPU failure can still require restarting DevJay or macOS.


## Claude permission popovers

In **Settings → IDEs & editors**, select the **Enable Claude prompts** checkbox. This single global setting applies to every folder and new Claude session; no folder-specific setup is needed. It installs an opt-in synchronous Claude Code `PermissionRequest` command hook in `~/.claude/settings.json` for Bash, Edit, Write and MultiEdit. Existing Claude settings and unrelated hooks are retained, with an exact `settings.json.devjay-backup-*` copy saved first. Clearing the checkbox removes this copy of DevJay's hook, releases pending requests to Claude, and rejects calls from sessions that still have the old hook loaded. Enabling another installed/development copy replaces the previous DevJay hook rather than creating competing approvers. If Claude has not reloaded its settings, restart that session. No rule is added to allow future commands automatically.

Hover the yellow IDE/Claude icon to read a pending request. If Claude only reports waiting and DevJay has no captured request, the popup explains that it must be answered in Claude and offers **Claude** and **Prompt settings…**. This includes questions already open before setup, unsupported prompts, a disabled integration, and requests returned to Claude after an unrecoverable disconnect, a longer app shutdown or expiry. The popup states when prompts are already enabled globally. Yes/No are shown only when DevJay has the actual request. Move into the popover to click **Yes** or **No**, in that order with Yes beside the originating icon. The Y, N and C in Yes, No and Claude are highlighted and underlined as shortcut hints. Yes still approves only the displayed request once. Yes/No is sent immediately; the selected button pulses for one second before the popup closes. With the pointer over the IDE/Claude icon or its open popup, **Y** immediately approves the displayed request once, while **N** denies it. No click or focus change is needed. Holding a key cannot answer subsequent requests. Only Y, N, C and Escape are temporarily registered while hovering; Enter, Space, other keys and Command/Control/Option shortcuts stay with the focused app. Leaving both regions unregisters the hover shortcuts. If another application owns a response shortcut, the popup explains that you can click it to use the keys locally. **Escape** dismisses without answering; hover again to reopen. After answering, leave the icon and hover again to review another waiting request. The default view shows a **Bash command** heading, Claude’s description and the full command, followed by **Do you want to proceed?** File requests show the path and before/after text or contents to write. Extra options remain visible, including background execution, timeout and replacement scope. **Show JSON** switches to the complete original tool input; **Show preview** returns without changing the request or resizing the popup. Long content scrolls. Descriptions come from Claude; DevJay does not independently verify what a command does.

**Claude**, or **C** while hovering or with the panel focused, returns the unanswered request to Claude, switches to the Site’s desktop, and brings its IDE or terminal forward. It does not send Yes or No. Exact terminal-tab selection is not currently available; if the host has several tabs, select the Claude tab there. A captured request can reconnect through a short DevJay restart: its original hook helper waits up to 30 seconds, then returns it to Claude if DevJay has not recovered. Reconnecting does not answer or run the request. The request also returns to Claude if the connection cannot be safely restored, it cannot be matched to a registered Site and supported IDE/terminal, or 24 hours pass. Clicking Claude or disabling the integration returns it immediately. Requests first raised while DevJay is closed stay in Claude. The former five-minute limit is upgraded automatically for an existing DevJay hook, preserving unrelated settings and custom timeouts. Requests already returned to Claude cannot be recaptured. Claude interruption removes the pending controls. Requests are kept in memory, never saved in DevJay configuration or logs.

Existing prompts are not replayed by installing a hook. Questions with choices, plan approval, sandbox network requests, unusually large tool inputs and unsupported tools stay in Claude. Ordinary activity detection still works without this integration. Turn **Show development app status** on to use the popovers.


## Updating DevJay

Installed copies check for a newer release after startup and every six hours. **DevJay → Check for Updates…** checks immediately and shows the result in Settings. When an update is available, choose **Update to <version>** in the strip or Settings. You can keep working while it downloads. When verification finishes, choose **Restart to update**. DevJay waits for confirmed Git operations to finish before quitting, installs the verified app, and reopens with your Sites and preferences preserved.

A failed check or download offers Retry. If DevJay is running from a disk image, a translocated location, or an application folder you cannot write to, **Download <version>** opens the releases page for manual installation. Move it into Applications before trying again. Development builds show their development status in Settings and never update themselves. If replacement fails after quitting, the helper restores and reopens the previous app where possible and retains its log and recovery files in a `.devjay-update-…` folder beside the app.

Release downloads provide separate ARM64 (Apple Silicon) and amd64 (Intel x86_64) DMGs and app ZIPs, with SHA-256 files. The terminal installer selects the native architecture even under Rosetta. Version 0.8.0’s built-in updater expects the former universal ZIP format; install the next release manually once to move to the architecture-aware updater.
